## Cloudflare R2 の利用方法（概要）

このプロジェクトでは、Cloudflare R2（S3 互換 API）を作品のサムネイル画像・動画ファイルの保存先として利用しています。サーバー側で AWS S3 互換クライアント（@aws-sdk/client-s3 の `S3Client`）を使い、PUT/DELETE 相当の操作を行います。

**目的**
- 画像・動画ファイルをオブジェクトストレージに保存し、アプリ側でプレビュー・再生・差し替え・削除を可能にする。

## 環境変数
サーバー側で R2 に接続するために以下を使用します（`process.env` 経由で参照）。

- `R2_BUCKET_NAME` — バケット名
- `R2_ACCESS_KEY_ID` — アクセスキーID（R2 の Access Key）
- `R2_SECRET_ACCESS_KEY` — シークレットキー
- `R2_ENDPOINT` — エンドポイント URL（例: `https://<accountid>.r2.cloudflarestorage.com`）
- `R2_PUBLIC_URL`（任意）— バケットを公開している場合のベース URL。未設定時は `R2_ENDPOINT` + `bucket` + `key` を組み立てて公開 URL を返しています。

環境変数は開発用に `.env.local` に置かれ、Next.js ビルド/サーバー実行時に読み込まれます。

---

## サーバー実装のポイント
- `S3Client` を R2 の `endpoint` と認証情報で初期化して利用しています（`@aws-sdk/client-s3`）。
- POST（アップロード）: `PutObjectCommand` 相当でファイルをバケットに書き込み、公開 URL と内部キー（オブジェクトキー）を JSON で返します。レスポンス例: `{ url: string, key: string }`。
- DELETE（削除）: 受け取った URL（または key）をもとに `DeleteObjectCommand` を投げ、オブジェクトを削除します。削除操作は認証済みユーザーのみ実行できるよう保護されています。
- アップロード時は Content-Type を適切に設定します（画像: `image/*`、動画: `video/mp4` など）。
- 所有権チェック: DB のエントリ所有者と一致するか、認可ロジック（`requireAuthWithRoles` 等）で検査してから削除を許可します。

---

## クライアント実装のポイント
- `WorkForm.tsx` では `uploadFile(file, kind)` が `/api/uploads` に `FormData` （`file` と `kind`）で POST し、戻り値の `url` をフォームにセットします。
- 既存ファイルを差し替える際は、新ファイルアップロード後に古い URL を `/api/uploads` の DELETE に渡して削除しています（UI 側でも即時に参照を消す）。
- アップロード呼び出しは、`supabase.auth.getSession()` で得たアクセストークンを Authorization: `Bearer <token>` ヘッダに付与して行います。サーバー側でこのトークンに基づく認証・認可を行います。

リクエスト例（アップロード）

POST /api/uploads (multipart/form-data)
- field `file`: ファイル本体
- field `kind`: `thumbnail` | `video`
- Authorization: `Bearer <access_token>`

成功レスポンス例

{
  "url": "https://.../bucket/path/to/object.jpg",
  "key": "uploads/thumbnail/2026/08/.../file.jpg"
}

削除リクエスト例

DELETE /api/uploads
Body: { "url": "https://.../bucket/path/to/object.jpg" }
Authorization: `Bearer <access_token>`

## UI 側の取り扱い（既存実装からの注意点）
- `WorkForm.tsx` はアップロード後に返された `url` を保持し、プレビュー表示に利用します。
- プレビュー表示では CSS 側で `object-fit: contain` 相当を使いアスペクト比が崩れないようにしています（例: `className="w-full h-auto max-h-40 object-contain"`）。
- 動画は `video` タグで `controls` を付け、同様に `object-contain` / `w-full h-auto` で表示しています。

## オブジェクトキー（保存パス）の形式と `xxx` の意味

現在の実装では、アップロード時にサーバー側でオブジェクトキーを次の形式で生成しています：

```
uploads/{kind}/{userId}/{timestamp}-{sanitizedFilename}
```

- `{kind}`: `thumbnail` または `video`（アップロード時に指定）
- `{userId}`: 認証中のユーザーの ID（`auth.identity.userId`）。ドキュメント中の `xxx` はこの `userId` を指します。これにより、ユーザーごとにオブジェクトが分離され、削除や所有チェックが容易になります。
- `{timestamp}`: `Date.now()` によるミリ秒タイムスタンプ（同名ファイル上書き防止、ソートに有用）
- `{sanitizedFilename}`: 元のファイル名から許可されない文字を `_` に置換した安全なファイル名。

例:

```
uploads/video/abc123/1691830456789-my_movie.mp4
uploads/thumbnail/abc123/1691830460000-profile_pic.png
```

セキュリティと運用上の効果:
- 削除 API はサーバー側で `key` のプレフィックスを検査し、`uploads/thumbnail/{userId}/...` または `uploads/video/{userId}/...` に一致しないキーの削除を拒否します。これにより、認証済みユーザーが他ユーザーのオブジェクトを削除することを防ぎます。
- ユーザーID をパスに含めることで、後で所有者別にオブジェクトを一覧・削除するバッチ処理が容易になります（R2 側でのプレフィックス検索が可能）。

注意点:
- 現在はユーザーID がオブジェクトキーに露出するため、公開 URL をそのまま公開している場合はユーザーID が推測可能になります。これが問題となる場合は、キー設計を変更してランダム UUID を使うか、バケット非公開＋プリサイン方式に移行してください。

## 制限・運用上の考慮点
- 署名付き URL（プリサイン）を導入すると、バケットを非公開にしても安全に一時的公開できます。現在は公開バケット（もしくは公開 URL をそのまま返す）実装のため、機密性を高めたい場合はプリサイン導入を検討してください。
- 大きな動画ファイルはクライアント→サーバー→R2 経由で転送されるため、サーバー帯域やアップロードタイムアウトに注意してください。必要ならクライアント直アップロード（ブラウザから R2 にプリサイン PUT）を検討します。
- コンテンツサイズ上限、ファイル種別の検証、ウイルススキャンなどは必須ではありませんが、運用要件に応じて追加してください。

---

## 推奨改善案
- バケットを非公開化して、サーバー側でプリサイン URL（短時間有効）を発行して返す（セキュリティ向上）。
- 大きなファイルは分割アップロード／進捗表示を検討する。
- アップロード失敗時のリトライやクライアント側のサイズチェックを追加する。
