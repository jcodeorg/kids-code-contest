`users` テーブルから初期値用フィールド（学校名・学年・保護者情報）をすべて削ぎ落とし、属性情報・保護者同意・作品番号の管理を **`contest_entries`（エントリーテーブル）へ完全集約した最新の差分仕様書**です。

# DB設計変更仕様書（`contest_entries` 完全集約版）

---

## 1. 概要・変更の背景

* **アカウント（`users`）と応募情報（`contest_entries`）の完全分離**
* `users` テーブルは「アカウント情報（誰がログインしているか）」のみを保持し、個人属性（学年・学校名）や保護者情報・同意管理はすべて **`contest_entries` テーブルに集約**しました。
* これにより、年度ごとの進学（学年・学校の変化）や、応募ごとの保護者・代理人（父・母・指導者等）の変更に完全対応し、学年更新漏れなどの運用事故を防ぎます。


* **作品番号（`work_number`）の「締め切り後発番」化**
* エントリー時点での即時自動採番（`NOT NULL`）から、締め切り後に事務局が一括採番する（`NULL` 許容）設計へ変更しました。
* 不備チェックや応募キャンセルに伴う欠番の発生を防止します。

### 応募・承認フローの流れ

```
[ Step 1: 子ども ]
   Googleログイン/新規登録
      │
      ▼
 [ Step 2: 子ども ➔ 保護者へ依頼 ]
   ・保護者のメールアドレスのみを入力して「同意・入力依頼を送る」を押下
   ・システム: `contest_entries` を生成（`status = 'draft'`, `guardian_consent = 'pending'`）
   ・システム: 保護者へ専用入力フォームのURL付きメールを送信
      │
      ▼
 ┌─────────────────────────────────────────────────────────┐
 │ （同時進行）                                            │
 │                                                         │
 │  [ Step 3-A: 保護者 ]                                   │
 │    ・届いたメールのURLを開く                             │
 │    ・「学校名」「学年」「保護者氏名」「電話番号」を入力   │
 │    ・規約に同意して送信                                │
 │      ➔ `guardian_consent = 'approved'` に更新           │
 │                                                         │
 │  [ Step 3-B: 子ども ]                                   │
 │    ・作品を制作・登録（`works` テーブル）                │
 └─────────────────────────────────────────────────────────┘
      │
      ▼
 [ Step 4: 子ども（または保護者） ]
   ・マイページで「同意完了」を確認し、制作した作品を選択して「応募提出」！
   ・システム: `status = 'submitted'`（正式応募完了）
```
---

## 2. テーブル別の役割と変更詳細

### ① `users` テーブル（ユーザーアカウント情報）

* **役割**: システムへのログインおよび認証・ロール管理のみに特化。
* **変更点**: `default_school_name` や `default_guardian_...` などの初期値用カラムをすべて削除し、最小限の構造へシンプル化。

### ② `contest_entries` テーブル（コンテスト応募データ）

* **役割**: コンテスト応募に関するすべての確定データ（属性・保護者・作品番号）を保持。
* **追加・変更カラム**:

| カラム名 | データ型 | 制約 | 変更点・役割 |
| --- | --- | --- | --- |
| **`school_name`** | `VARCHAR(100)` | `NOT NULL` | 応募時に保護者/本人が入力した学校名 |
| **`grade`** | `VARCHAR(10)` | `NOT NULL` | 応募時に選択した学年（例: `p1`〜`m3`） |
| **`guardian_name`** | `VARCHAR(100)` | `NOT NULL` | 今回の応募における保護者氏名 |
| **`guardian_email`** | `VARCHAR(255)` | `NOT NULL` | 今回の応募における保護者メールアドレス |
| **`guardian_phone`** | `VARCHAR(50)` | `NOT NULL` | 今回の応募における保護者電話番号 |
| **`guardian_consent`** | `ENUM` | `NOT NULL DEFAULT 'pending'` | 保護者同意ステータス（'pending', 'approved', 'rejected'） |
| **`guardian_consent_at`** | `TIMESTAMP` | `NULL` | 保護者同意完了日時 |
| **`guardian_consent_token`** | `VARCHAR(255)` | `UNIQUE` | 保護者承認用トークン |
| **`guardian_agreed_ip`** | `VARCHAR(45)` | `NULL` | 同意時のIPアドレス |
| **`work_number`** | `INT` | **`NULL` 許容** | 作品番号（#100〜）。応募時は `NULL` で保存し、締め切り後に事務局が一括発番 |

## 3. 確定版 DDL（SQL）

```sql
-- 保護者同意ステータス用の列挙型定義
CREATE TYPE guardian_consent_status AS ENUM ('pending', 'approved', 'rejected');


-- 1. users テーブル（アカウント認証情報のみ保持する最小構成）
CREATE TABLE users (
    user_id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) NOT NULL UNIQUE,          -- アカウント統合のキーとなる一意アドレス
    auth_provider VARCHAR(50) NOT NULL DEFAULT 'email', -- 'google', 'email', 'multiple'
    name VARCHAR(100) NOT NULL,
    name_kana VARCHAR(100),
    
    -- 現在選択中のロールID
    current_role_id VARCHAR(30) NOT NULL DEFAULT 'applicant',
    is_active BOOLEAN NOT NULL DEFAULT true,     -- アカウント有効化フラグ
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);


-- 2. contest_entries テーブル（属性・保護者同意・作品番号を集約）
CREATE TABLE contest_entries (
    entry_id BIGSERIAL PRIMARY KEY,
    contest_id BIGINT NOT NULL,
    work_id UUID NULL,                 -- Step 4 の作品提出時にセット（初期は NULL 許容）
    user_id UUID NOT NULL,
    
    -- ★ Step 3-A で保護者が入力するため、エントリー作成直後は NULL 許容
    school_name VARCHAR(100) NULL,     -- 応募時の学校名
    grade VARCHAR(10) NULL,            -- 応募時の学年
    guardian_name VARCHAR(100) NULL,   -- 保護者氏名
    guardian_phone VARCHAR(50) NULL,   -- 保護者電話番号
    
    -- Step 2 の段階で必須入力・保存される項目
    guardian_email VARCHAR(255) NOT NULL,                 -- 子どもが指定した保護者メールアドレス
    guardian_consent guardian_consent_status NOT NULL DEFAULT 'pending',
    guardian_consent_at TIMESTAMP WITH TIME ZONE NULL,
    guardian_consent_token VARCHAR(255) UNIQUE NOT NULL, -- 承認・入力フォーム用トークン
    guardian_agreed_ip VARCHAR(45) NULL,                  -- 同意時のIPアドレス
    
    -- 作品番号（締め切り後に事務局が発番）
    work_number INT NULL,
    
    entry_type VARCHAR(10) NOT NULL DEFAULT 'individual',
    team_name VARCHAR(100) NULL,
    team_members TEXT NULL,
    status VARCHAR(30) NOT NULL DEFAULT 'draft',          -- 初期値は 'draft' (準備中)
    is_primary_passed BOOLEAN DEFAULT FALSE,
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP,
    
    CONSTRAINT fk_entries_contest FOREIGN KEY (contest_id) REFERENCES contests(contest_id),
    CONSTRAINT fk_entries_work FOREIGN KEY (work_id) REFERENCES works(work_id),
    CONSTRAINT fk_entries_user FOREIGN KEY (user_id) REFERENCES users(user_id),
    CONSTRAINT uq_contest_user UNIQUE (contest_id, user_id)
);

-- インデックス定義
CREATE INDEX idx_entries_consent_token ON contest_entries(guardian_consent_token);
CREATE INDEX idx_entries_work_number ON contest_entries(contest_id, work_number);

```

## 補足： コンテストのコンテキスト（コンテスト選択）仕様

* **単一のアクティブコンテスト管理:**
  * `contests` テーブルに `is_active BOOLEAN NOT NULL DEFAULT false` を持ち、同時に **1件だけ** `is_active = true` を許可する。
  * そのコンテストを `active_contest` と定義し、応募者 (`applicant`)、審査員 (`staff`, `judge`) の全操作は、明示的な指定がない限り自動的にこの `active_contest` を対象にする。
  * 画面側のデフォルト選択・一覧表示・応募処理・採点処理はすべて `active_contest` を優先して動作させる。
* **表示上の配慮:**
  * Navbar に、現在アクティブなコンテスト名（例: 「2026年度 コンテスト」）をバッジで表示する。
  * 管理者画面では「アクティブ」状態を見える化し、現在の対象大会が明確になるようにする。
* **コンテスト切り替え（管理者用）:**
  * `contest_admin` の管理画面においてのみ、アクティブコンテストの切替、年度追加、既存コンテストの更新を可能とする。
  * 新年度コンテストの作成時には、必要に応じて `is_active = true` を設定し、既存の有効コンテストを自動的に `false` に切り替える。
* **運用ルール:**
  * `applicant` / `staff` / `judge` は通常、ユーザーが明示的に別コンテストを指定しない限り、`active_contest` を使って業務を行う。
  * 例外的に、管理者が明示的に `contest_id` を指定した場合はその値を優先する。
